# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"আমার বাংলাদেশ" — a mobile-first, Bangla-language site with two pillars:
1. **The quiz** "তোমার বাংলাদেশ কোথায়?": a 1-minute personality quiz that matches a player to one of 9 Bangladesh places, then pushes them to share the result (**quiz → result → share → friend plays**). It is the emotional identity and the growth engine; since 2026-10-10 it lives at `/quiz` (the Quiz menu), and results and friend links stay at `/r/{code}`.
2. **The community** (added 2026-10-09; the home page `/` since 2026-10-10): Bangladeshis ask questions, answer, and browse a feed (**discover → ask → receive answers → browse**). Reading is open; writing needs a login (Google, Facebook, phone code or email), and posts/answers can be anonymous. Built: threads (replies), editing, search, notifications, the division map, formatted posts/answers, photos. The community-first redesign runs in phases (`docs/2026-10-10_community-first-plan.md`, local only): 1–4 done, 5 rich text built (goes live after the owner's Android keyboard test; if it fails, a Markdown toolbar replaces the Tiptap composer), 6 photos done (video later), 7 hardening: speed check, accessibility and dashboard done. Second feature plan (`docs/2026-10-10_feature-plan.md`, owner's answers in it): chunks 1–7 done (first wave: saved posts, share polish, moderation log + badge, community health panel, view counts, notification preferences, topic admin); next the Bangladesh-specific second wave, chunk 8 announcements, then 9 → 14 in order. Not planned: follows, groups, ranking — don't add them unasked.

The whole site is **Bangla at `/…` and English at `/en/…`**. The quiz needs no login; no XP or global leaderboards.

## Architecture

**Home** (`/`, `PageController::home`, `community/home.blade.php`): the community first. Two columns on desktop that flow independently (left: hero, ask, picked area, lists; right: map card, topics, quiz promo); one column on phones ordered with `order-*` (the columns are `contents` there). The hero has the flag motif (`.home-glow`, `.home-sun`, `.mini-flag`) and staggered entrance (`.home-in`, `.home-cards`). All motion is off under `prefers-reduced-motion`. The hero's ask box is a GET form to `/ask?title=` (works without JS) with the Ask page's `similarQuestions` under it; then three numbers (posts, answers, solved; cached 5 min, `countUp` animates them once) and a "happening now" ticker of the 8 newest posts (`ticker`, one at a time, pauses on hover/focus, still under reduced motion). The whole home grid is one `divisionMap` scope (community.js), so the map, the picked-area panel and the lists share `topic`.
**The map** (`partials/division-map`, `App\Community\DivisionMap`): real division shapes (`resources/data/bd-divisions.php`, `scripts/build-division-map.py`) in the same Mercator projection as `partials/bd-map`, shaded by discussion count (`data-level` 0–4, `--div-*` tokens; an attribute, not a class, so the topic lens can change it), names on the shapes, a pulse where people posted in the last 7 days, one hover/focus label (`tip`: counts + the newest question title). Tapping a division zooms in (animated `viewBox`, box from the shape's `getBBox()`) and draws its districts from `GET /api/map/{division}[?category=]` (`partials/district-map`, plain links with no Alpine; the `districts` group listens; shapes in `resources/data/bd-districts.php` from geoBoundaries ADM2 via `scripts/build-district-map.py`); "← সারা দেশ" or Escape zooms out; strokes use `vector-effect: non-scaling-stroke`. Picking a division or district loads its latest posts from `/api/feed` into `partials/division-posts` (cached per area+topic, old posts dimmed while loading, a skeleton only after 250 ms), which steps to the previous/next area with ‹ › or a swipe. Topic lens: chips above the map (and the topic tiles) set `topic`, which re-shades the divisions from `DivisionMap::lens()` (every topic's levels in the page), refetches the zoomed districts and the panel, and swaps the home lists for that topic's (`homeLists`, `/api/feed?tab=&category=`). Counts come from one cached (5 min) query grouped by area and category (`DivisionMap::counts()`), newest titles from the last 400 posts with a place (`latest()`). Without JS every division, chip and tile is a link to its feed. The quiz keeps its own outline map.

**Single-page quiz.** `/quiz` and `/r/{code}` both render `resources/views/site/app.blade.php`, which embeds all questions/locations as JSON (`#boot`) and runs one Alpine component (`resources/js/quiz.js`) with screens `landing | teaser | question | reveal | result`. Only one API call happens per play (`POST /api/results`). After it, the URL is `pushState`d to `/r/{code}` — the result URL *is* the share URL. On `/r/{code}` the client decides owner vs visitor: owners have the code in `localStorage['bd.mine']` (with their owner token); everyone else sees the teaser, and their own play is sent with `ref` so they get a friend-match %. The teaser is kept compact so its play button sits above the fold on a phone (inside Messenger's browser too); it challenges the visitor to see how much they match the friend and shows how many friends already played from that link (`friendPlays`, one count query in `QuizController::show`). The landing page follows the same rule: on phones the map's height is capped so the play button is above the fold (checked at 360×560), and it shows the total play count (`QuizController::totalPlays()`, cached 10 min) only from `SHOW_PLAYS_FROM` (100) plays, since a small number is weak social proof.

**Public routes are cookieless and sessionless** (`routes/web.php` strips session/cookie/CSRF middleware). That's what makes pages CDN-cacheable and is the privacy model. Don't add `session()`, `csrf_token()`, `$errors` or auth checks to public views. The only write needing ownership (`PATCH /api/results/{code}/name`) uses a per-result owner token (stored hashed). Admin (`routes/admin.php`) uses normal session auth; every user is an admin, there is no registration. One permanent **super admin** (`config/admin.php`, same identity as the hospital-management project) is guaranteed by `App\Support\SuperAdmin\SuperAdminProvisioner`: after every `migrate` (listener), in `DatabaseSeeder`, via `admin:ensure-super-admin`, and throttled on boot. Its password comes only from `SUPER_ADMIN_PASSWORD` (never commit one: the repo is public); `User` refuses to delete, demote or re-address it, and `is_super_admin` is not fillable.

**Scoring** (`app/Quiz/`) is deterministic and server-only:
- 8 trait dimensions (`traits` table). Each answer has `trait_weights`; each location has a 0–10 `profile`.
- Result = location with highest cosine(player vector, profile) + `BONUS_WEIGHT × location_bonus` (small "signature answer" nudges, e.g. ইলিশ → বরিশাল).
- `QuizConfig` is an array snapshot of active content, cached forever (as arrays — the cache refuses to unserialize objects). **Any content write must call `QuizConfig::forget()`**, which also flushes the embedded quiz JSON (`quiz.boot`) and trait labels.
- Displayed match % is a calibrated "vibe match" (72–97), not raw similarity; friend match is calibrated on random pairs. Both are in `Scorer`.
- Results store their computed output (location, %, traits, reason, `scoring_version`), so editing content never changes old shared results.
- **Balance matters**: every location should win 6–18% of all answer combinations, both uniformly and when players favour the adventurous answers (`Simulator::run(Simulator::FAVOURED_TRAIT)`: the most-adventure answer per question picked 35% of the time; at launch real players did this and বান্দরবান won 47%). `ScoringTest` enforces both; the admin Balance page (thin bar) and `quiz:simulate` (last column) show both. The editors' live preview only shows the uniform case. After changing weights/profiles, re-check. Content changes that must reach production go in a data migration too: deploys run `migrate`, not the seeder (see `2026_10_08_000002_rebalance_adventurous_answers`, which skips rows edited in admin). `App\Quiz\Replay` (Balance page, "Real players, replayed") re-scores each player's latest stored answers with the current content, shows what they got vs would get now, and the real adventurous-answer pick rate to check the 35% assumption; it uses `Simulator::favouredOptions()` so both share one definition, and only flags shares once `Replay::TRUSTED` (100) players exist.

**Share cards**: PHP GD cannot shape Bangla conjuncts. So the shareable card is drawn client-side on canvas (`resources/js/card.js`) in two formats, a 1080×1920 story and a 1080×1080 square for feed posts: 4 designs (`resources/js/cards/{passport,poster,boarding,minimal}.js`; the default export draws the story, the named `square` export the square layout; shared helpers in `common.js`) × 6 colour themes (`cards/themes.js`; `place` = the location's own accent, the original look). Templates take a resolved palette `t` (`ink`/`accent` for the background, `cardInk`/`cardAccent` for white panels so dark themes stay readable); all theme colours must be 6-digit hex because templates append alpha. `renderCard(result, {template, theme, format, scale})` — `scale` draws the small picker previews; use `shadow()` from `common.js` rather than raw `shadowBlur` so shadows scale too. The card is built as soon as a result shows (desktop shows it as the left column, with the place illustration as a placeholder until it's drawn; phones show a thumbnail) and re-drawn after the name is typed. On phones a floating share button appears once the result's own share button has scrolled up out of view (`watchShareButton()`/`showFab`; a scroll check, since a fling can skip an IntersectionObserver). A result played from a friend's link shows the friend match right under the headline, with "send yours to <name>" (`replyToFriend()`, tracked as `share_clicked` channel `friend`). The share sheet shows design previews and colour swatches; choices are kept in `localStorage` (`bd.card`, `bd.theme`, `bd.format`) and sent as `template`/`theme`/`format` in `card_saved`/native-share event meta.

**Bangla text rendering**: Open Graph images are pre-rendered per location with headless Chrome (`quiz:og-images`, view `og/image.blade.php`). Personalisation in link previews is only in `og:title` text. Bangla digits/possessives: `App\Support\Bangla` (PHP) mirrored in `resources/js/bn.js` — keep them in sync.

**Share handling**: Facebook/Messenger/Instagram in-app browsers block downloads and file sharing; `share.js` detects them and the UI falls back to "long-press the image to save". Native `navigator.share({files})` is used where available.

**Analytics** are first-party and cookieless: the client batches events to `POST /api/events` with `sendBeacon` (text/plain body); allowed names are `AnalyticsEvent::CLIENT_EVENTS`. `quiz_completed` is recorded server-side. Visitor identity is a random UUID in localStorage; no IP or user agent is stored (only a coarse device class). `App\Analytics\Funnel` builds the admin dashboard: funnel steps are distinct visitors (completed = completers among the period's starters, so rates stay ≤ 100%; `plays` is the raw result count), it takes an optional `$until` for the previous-period comparison, referral numbers (`referred_players`, `referral_conversion`, `viral_k`) count distinct people so replays don't inflate them, `startRateByEntry()` splits the start rate into landing vs friend-link visitors (via the `referred` flag on `quiz_started`), and `trend()` gives daily (weekly past 60 days) rows for the SVG chart in `admin/partials/trend-chart.blade.php`. Raw events are pruned after 180 days (scheduled `model:prune`). With months of events (checked with ~500k) the dashboard is the slow page: queries lean on the `(created_at, visitor_id)` and `(name, created_at, visitor_id)` indexes (keep new "distinct visitors since X" queries on those columns), and `DashboardController` keeps each range's numbers in the cache (key `admin.dashboard.v2.{days}`: bump the version when the cached arrays change shape) (`CACHE_SECONDS`, 2 min for today up to 1 h for a year; "count now" = `?fresh=1`) as plain arrays; recent plays stay live. Server-side events go through `AnalyticsEvent::server()`, which takes the visitor id from the `X-Visitor` header (community.js sends it on writes; Google/Facebook carry it as `?v=` through the session), so `signed_up`, `post_created` and `answer_created` join the quiz journey. `Funnel::community()` is the dashboard's "Quiz → community" panel: quiz players → clicked into the community → viewed → signed up → posted/answered (each step a subset of the one before), plus community visitors/writers who played, returning visitors (seen on 2+ days) and clicks by place.

**Community health** (dashboard panel, `App\Analytics\CommunityStats`): counted from the community tables, not events. New members / posts / answers per day (per week past 60 days), posts by weekday, time to first answer for question + help posts (first published top-level answer by someone other than the asker; median over answered posts, "within 1 h / 24 h" only over posts at least that old, unanswered shown separately), and report handling (first report → first admin action, from the moderation log's `meta.first_report_at`, so only from 2026-10-10; plus items waiting now and their oldest report). Cached with the other numbers, except report handling, which the controller counts live so "waiting now" is current. `created_at` indexes on members, posts and answers (migration 000018).

**Result page explore**: `ResultPresenter` adds `places` (every place with this player's % and the answers that pulled toward it, from `Scorer::explore()`; stored winner/runner-up keep their %, others are capped below) and per-trait `answers`; the client resolves option ids to labels from the boot JSON. The same place sheet opens from landing cards in preview mode (no %). Note: MySQL JSON columns don't keep key order, so sort `trait_scores` before use.

**Community** (`app/Community/`, `Site/Community/*Controller`, `resources/views/community/`, `resources/js/community.js`):
- **Accounts without cookies**: a `Member` signs in with one or more `member_identities` (`google` | `facebook` | `phone` | `email`; `App\Community\Accounts`), and each signed-in browser holds a random token (`member_tokens`, stored hashed) in `localStorage['bd.member']`, sent as `X-Member-Token`. Middleware `member` accepts any known token, `member:account` (every community write) needs a signed-in account. No cookie, so no CSRF, and community pages stay cacheable/cookieless. Only `/auth/{google,facebook}/{redirect,callback}` use a session (Socialite's OAuth state); they hand the token to `/auth/done#t=…` in the fragment. Phone codes go through `App\Support\Sms\SmsSender` (`log` locally, `bulksmsbd`); email has register/login/forgot/reset (reset link `/reset-password#t=…`). A method appears only when its keys are set (`Accounts::providers()`; setup steps in `.env.example`). Members created before login existed have no identity: they can't write, and signing in on that browser merges their posts into the account (`Accounts::absorb`, `POST /api/auth/link`). `users` stay admin-only. In the browser, any write calls `call()`, which opens the sign-in sheet (`partials/login-sheet`) and resumes the action afterwards; text typed before a Google/Facebook round trip survives via `form[data-draft]`.
- **Anonymous posts/answers** (`is_anonymous`): the public sees "বেনামী" (`partials/author`), and the member's code/name never appear in public HTML; owner controls come from `POST /api/mine` (which of these `post:ID`/`answer:ID` are mine) for all content, never from codes in the page. Profiles skip anonymous items, counts included. Admins see the real author.
- **Threads** (Phase 4): a reply is an `answers` row with `parent_id` (what it answers: an answer or another reply) and `thread_id` (its top-level answer); there is no separate comments table. `posts.answers_count` counts top-level answers only (so "unanswered" keeps its meaning) and only they can be the solution; a top-level answer's `replies_count` counts its thread's published replies (`Answer::refreshReplyCount()`, also run by `Moderation::setStatus()`). The post page pages top-level answers (20, solution first, then most helpful) and loads each thread's first 3 replies in one query (ROW_NUMBER window); "show more" calls `GET /api/answers/{id}/replies?after=` (HTML from `partials/reply`); `?thread=ID` (from reply notifications) opens a whole thread. Display is one level deep: a reply to a reply says "↪ to <name>" instead of indenting further. A taken-down answer that still has replies stays as a placeholder. Partials: `thread` (answer + replies + reply box; holds `replyTo`/`more`/`after`), `answer`, `reply`, `edit-form`. Replies notify the author of what they answer (`reply`, site only, never emailed). **Editing**: authors edit posts (title, details) and answers/replies (`PATCH /api/posts/{id}`, `/api/answers/{id}`), which sets `edited_at` ("(edited)"); the editor text comes from a `<template data-raw>` holding exactly what was written.
- **Rich text** (Phase 5): posts and top-level answers can carry `body_html` (bold, italic, lists, links; posts also `h3`), sent by the editor with `format=html` and cleaned by `App\Community\RichText` (HTML Purifier allowlist, http/https/mailto only, nofollow + new tab, bare URLs linked). `body` always holds the plain text (`RichText::toText()`), which excerpts, search, similar questions, the duplicate check and emails use; link limits count the HTML's `<a>` tags. `body_html` NULL = plain text (old rows, no JS, replies, which always stay plain). Render bodies with `RichText::render($item)`, never `Text::render($item->body)`; `.prose-text` styles the tags. Editing: items carry `<template data-raw-html>` beside `data-raw`; edit forms fill the textarea with the plain text (`editText()`, so editing works if the editor chunk never loads) and `x-rich.now` opens the editor on the formatted version (unless the plain text was changed meanwhile); the editor is destroyed when the form closes. Saving a plain edit clears `body_html`. `post_created`/`answer_created` carry `rich` (1 when `RichText::isFormatted()`), shown on the dashboard as the share of writes that used formatting. Bangla pages number lists with Bangla digits (`:lang(bn)`). Demo bodies are formatted by `DemoContent::bodies()` ("• " / "১. " lines become lists, `**bold**`, `*italic*`).
- **Photos** (Phase 6, done 2026-10-10; video later): up to 4 per post or top-level answer (`App\Community\Photos`, `photos` table, `photoable_type` post|answer). Uploaded first (`POST /api/photos`, `throttle:photos`; the browser shrinks them first), attached when the post/answer is saved (`photos[]` ids: the member's own unattached ones or ones already on that item; absent on edit = unchanged, `[]` = remove all). Every upload is decoded with GD and written again as WebP, `{path}-full.webp` (1600 px) and `-thumb.webp` (480 px) on the public disk under `photos/Y/m/`, so no metadata survives; JPEG EXIF rotation is applied first. None on anonymous items or replies. The author deleting an item deletes its files at once (`Moderation::setStatus`); after an admin removal they stay 30 days (restorable), then `community:prune-photos` (hourly) deletes them, along with uploads never attached after 24 h and photos whose item is gone. The public disk is group-writable (`config/filesystems.php`) so the scheduler can delete what the web server wrote. Deploy needs `php artisan storage:link`. Composer: `partials/photo-picker` (Ask, the answer box, both edit forms; `fromItem` starts from the item's `<template data-raw-photos>`) runs `photoPicker` (`resources/js/photos.js`): shrinks in the browser (1600 px JPEG, upright), uploads at once with progress (`uploadPhoto` in community.js), and `formPayload()` sends `photos` (waits while uploading). Forms declare `photoCount` so the anonymous switch locks while photos are attached, and the picker is off while anonymous is on. Display: `partials/photo-grid` (post: `big`, one photo keeps its shape, 2–4 a grid; answers: a small row) links each photo to its full file and, with JS, opens the one shared viewer (`partials/photo-viewer`, `viewer`/`openPhotos`/`stepPhoto` in community.js: arrows, swipe, Escape, x-modal focus). Cards show the first thumbnail and "+N" (eager-load `photos` wherever cards are listed: Feed, Search, related, profile). A post's first photo also gets a JPEG copy (`-share.jpg`, `Photos::SHARE`) used as its `og:image` (`ogImageSize` sets the real size). /admin/community shows thumbnails of reported items. `Photos::store` checks every file write (the disk doesn't throw) and fails rather than save a row without its file. Demo content gets drawn scenes (`App\Community\DemoPhotos`, `photos` key in the demo data) through the same upload path, so tests that seed it need `Storage::fake('public')`. Deploy steps (storage:link, upload limits, backups): `deploy/FORGE.md`.
- **Saved posts** (feature plan chunk 1): `saved_posts` (member, post, unique), private. `POST /api/saved` {post, saved: bool} (idempotent; only published posts can be saved), `GET /api/saved?before=` (rendered with `partials/post-list`, newest saved first, taken-down posts drop out and come back if restored), `/saved` is a cacheable shell like `/notifications` (linked from the owner tools on the profile). `/api/mine` also returns `saved` for the posts on the page. The bookmark (`[data-save]` in `partials/post-card` and on the post page) is plain HTML because cards are also fetched into the quiz page: the `community` component handles its clicks, paints `.is-on`/`aria-pressed` (a MutationObserver repaints fetched cards), keeps ids in `localStorage['bd.saved']`, and shows the button only via `html[data-card-actions]`. Deleted with the account. Events `post_saved`, `saved_view`.
- **Sharing** (feature plan chunk 2): `sharePost(title, url, from)` uses the phone's native share sheet only on mobile outside in-app browsers; otherwise it opens the community layout's share sheet (WhatsApp, Facebook, Messenger, copy, a selectable link field with a long-press hint in Facebook/Messenger's browsers, where links open in place since new windows are blocked). Cards carry a plain-HTML share button (`[data-share]` + `data-title`, handled by `watchCardButtons()` like the bookmark). `post_shared` meta: `channel`, `from` (post | card). Link previews: posts are `og:type=article`; community pages without their own photo use `images/og/{,en/}community.png` (`quiz:og-images --only=community`), the quiz keeps `default.png`.
- **View counts** (feature plan chunk 5, `App\Community\Views`): `posts.views_count`. Post pages are cached, so the page reports the view (`[data-post-view]` → `countView()` → `POST /api/posts/{id}/view` with `X-Visitor` and, if signed in, `X-Member-Token`; `throttle:views`). Counted once per visitor per post per day (cache key = sha256 of post + visitor id, never stored with the post), never for the author, bots (`Device::fromUserAgent`), a missing/invalid visitor id or unpublished posts; incremented through `toBase()` so `updated_at` stays. Shown on the post from `Views::SHOW_FROM` (10). `post_view` events carry `meta.post`. Dashboard: views by topic and most read (`CommunityStats::views()`, posts created in the range). Cleared browser storage counts again (stated in the panel and the privacy page).
- **One `posts` table** for every kind (`Post::TYPES`: question, discussion, tip, help); a new kind is a TYPES entry, not a table. `answers` are replies to any kind. Statuses (both): `published | hidden | removed | deleted` (string column, no soft deletes). Anything that adds columns to `posts` must set `innodb_ft_enable_stopword = OFF` in that session first (see Search below; `2026_10_10_000011` shows how). `answers_count` is denormalised, recomputed by `Post::refreshAnswerCount()`; `Moderation::setStatus()` does that for answers, so always change status through it.
- **Trust, not likes**: one `helpful_marks` table (`markable_type` post|answer) labelled "কাজে লেগেছে"/"আমারও জানা দরকার"; the post's author can mark one answer as the solution (`accepted_answer_id`). Profiles show helpful/solved/answers/posts. Keep new engagement signals pointed at helpfulness.
- **Moderation**: `reports` (one per member per item); `Moderation::AUTO_HIDE_REPORTS` (3) distinct reports hide an item until an admin keeps (clears reports) or removes it on `/admin/community`, which can also block a member (`blocked_at`, writes then 403). Every admin action (hide/restore/remove/keep/block/unblock) and every automatic hide is written to the append-only `admin_actions` log by `Moderation::log()` (called *before* the action, since a keep deletes the reports; `meta` keeps the status before, title, report count, reasons and `first_report_at`), shown read-only at `/admin/community/log`. The admin sidebar's Moderation item shows a "need a look" badge (`Moderation::needsLookCount()`, cached 60 s, cleared by `setStatus()` and `report()`). Writes are throttled per IP (`members`, `posts`, `answers`, `community`, `reports` limiters); posts/answers allow ≤ 2 links; an identical post/answer by the same member within 10 minutes is returned instead of duplicated.
- **Feed** (`App\Community\Feed`): newest first, keyset (`cursorPaginate`) by id within a status, narrowed by tab (`latest`, `unanswered`, `solved`), category and area (a division includes its districts). New tabs (popular, near you…) go in `Feed::TABS` + `posts()`. Pages are server-rendered Blade (indexable; `?cursor=` pages are `noindex`). **Endless lists** (feed, profile tabs, search): `partials/more` renders `<a data-next href>` (works without JS); `resources/js/infinite.js` fetches that next page's normal HTML, appends the list's `[data-item]` children it doesn't have yet, auto-loads 4 pages then shows the button (so the footer stays reachable), and restores the loaded list + scroll on back (sessionStorage). Give every list item `data-item="type:id"`. Previews (home map, result page) call `GET /api/feed`, which returns **HTML rendered from the same partials** (`partials/post-list`, `post-card`), and `POST …/answers` returns the rendered `partials/answer` — the client never re-implements a card. Owner-only controls are shown client-side by comparing the member code, so pages need no per-user rendering.
- **Search** (`App\Community\Search`, `/search`, `noindex`): MySQL FULLTEXT `posts_search` (title, body) **with the ngram parser** (works for Bangla without a dictionary); every query word is matched as a phrase (= substring), all required. The index is built with `innodb_ft_enable_stopword = OFF` (with ngram, chunks containing stopwords like "a"/"i" are dropped, breaking English); anything that recreates `posts` (TRUNCATE, a table-copy ALTER) rebuilds it with stopwords back on unless that session sets it off too, and FULLTEXT never sees uncommitted rows, so `SearchTest` commits and cleans up with DELETE instead of using RefreshDatabase. `Search::posts()` ranks matching ids in one narrow FULLTEXT pass (up to `MAX_RANKED`) that also gives the total, then loads only the page's posts. `Search::similar()` feeds "has this been asked?" on the Ask page (`GET /api/posts/similar`, throttled) on its own title-only index `posts_title_search` (ngram, also built with stopwords off): any meaningful word (stopword lists in Bangla and English), then titles sharing the most words. Events: `search_performed` (result count and query length only, never the text), `similar_shown`, `similar_clicked`, `feed_page_loaded`, `feed_load_failed`.
- **Taxonomy**: `categories` and `areas` (one tree: division → district; upazila later, `type` column), first inserted by a migration (`2026_10_09_000002_*`), cached as arrays in `Taxonomy` (call `Taxonomy::forget()` after editing them). Categories ("Topics") are managed at `/admin/categories` (feature plan chunk 7, `Admin\CategoryController`): add (slug from the English name, fixed after), rename bn/en, emoji, order, on/off; never deleted; every change logged in `admin_actions` (`topic_add|topic_edit|topic_off|topic_on`, `meta.changes`). `Taxonomy::categories()` = active only (Ask, filters, lens, tiles); `Taxonomy::allCategories()` includes turned-off ones, which `Feed::fromRequest` uses so old `/feed?category=` links still filter; posts keep their tag.
- **Quiz ↔ community**: the home page carries the quiz promo and the site navigation has a Quiz item; the quiz landing (`/quiz`) no longer embeds community posts (the tab bar links there). The result page invites into the community only after everything else, about the player's place: each `Location` has an `area_slug` (a district, or a division for places spanning several; editable in the Location editor, in the boot JSON as `area`), so the block shows that area's posts (falling back to the latest with a "be the first to ask" line) and links to `/feed?area=…` and `/ask?area=…&category=travel` (`communityLink()` in quiz.js; divisions are left out of the ask link since its select lists districts). The place sheet links to the place's discussions too; place clicks carry `meta.place`. Both lazy-load posts via `community-preview.js` so the quiz's cached HTML is unchanged. Feed and post pages carry a quiz promo card. Clicks are tracked as `community_clicked`; community page views as `home_view`/`feed_view`/`post_view`/`ask_view`, writes as `post_created`/`answer_created` (server-side).
- **Notifications** (`member_notifications`, `App\Community\Notifier`): `answer` (your post was answered), `accepted` (your answer is the solution), `need` (a question you pressed "আমারও জানা দরকার" on got an answer; one unread per question, site only). Nobody is told about their own action. Hidden/removed answers drop out through `MemberNotification::visible()` (not deleted, so a restore notifies again). On the site: a dot on "আমি" (`GET /api/notifications/unread` once per page) and `/notifications`, a cacheable shell whose list comes from `GET /api/notifications` as HTML (`partials/notification`); opening it marks all read. Email: `community:send-notification-emails` (scheduled every 5 min, no queue worker) sends one email per member per post after a 5-minute wait, skipping notices already read, at most one per post per 6 h and 5 a day (`SendNotificationEmails` constants), in `members.locale` (remembered on sign-in/post/answer), with a signed unsubscribe link (`/notifications/unsubscribe/{code}`: GET asks, POST/one-click turns `email_notifications` off). Per-kind choices (feature plan chunk 6): `members.notification_prefs` JSON stores only what's off (`{"site": {"reply": false}, "email": {"answer": false}}`, null = all on); `Member::wantsNotice($channel, $type)` is checked by `Notifier` (site off = no notice, so no email either) and by the email command (`EMAILED_TYPES` = answer, accepted; also needs an address and `email_notifications`). Switches on `/notifications` (`setNoticePref`), saved through `PATCH /api/notifications/settings` {`email`?, `prefs`?}. `members.email` is the verified address (email sign-in, or Google/Facebook's), hidden and only for these emails; phone-only members get site notifications only.
- **Privacy & account deletion**: `/privacy` (text in `community/privacy/{bn,en}.blade.php`, keep it true to the code; bump `PageController::PRIVACY_UPDATED` when it changes; contact address `config('admin.privacy_email')`) is linked from both footers, the sign-in sheet and notification emails, and is the URL to give Facebook/Google as privacy policy and data-deletion instructions. A member deletes their account from their own profile (`DELETE /api/members/me` with `confirm` = their code; `Accounts::delete()`): identities, email, password, tokens, notifications, helpful marks and reports go (counts decremented); posts/answers are deleted only if they tick the box, otherwise they stay with the author shown as "মুছে ফেলা অ্যাকাউন্ট" (`members.deleted_at`, `Member::isDeleted()`; the code is rotated and the profile 404s). `Notifier` skips deleted members. Eager-load `deleted_at` with `member:` relations that feed `partials/author`.
- Community copy uses আপনি (the quiz keeps তুমি). `Bangla::ago()`/`Bangla::date()` give relative times (PHP only).

**Languages** (`App\Support\Lang`, `resources/js/i18n.js`): every page route is registered twice, plain (Bangla) and under `/en` with names prefixed `en.`; use `lroute()` (not `route()`) for public links and `path()` in JS. `SetLocale` takes the language from the URL, from `X-Locale` on POSTs, or `?lang=en` on cacheable GETs (`/api/feed`). Interface text uses JSON translations with **the Bangla text as the key** (`__('…')` in PHP/Blade, `t('…')` in JS) and `lang/en.json` for English; English pages load that file as a separate JS chunk. Counted phrases go through `Lang::choice(':nটি উত্তর', $n)` / `t(key, { n, count })` with "singular|plural" English values (don't use `trans_choice` directly: for a key missing from a Bangla file it falls back to English). Use `Lang::num/ago/date/possessive` instead of the `Bangla::` versions in views. Where one Bangla phrase needs two English meanings, use a context key with a `lang/bn.json` entry (`post.type.*`). Quiz content has `*_en` columns (`Bilingual::text('title')` falls back to Bangla; `Location::localizedBadges()`); presented/boot data use neutral keys (`name`, `title`, `tagline`, `description`, `label`) already in the page language, and the boot JSON/trait labels are cached per language. Results store `reason_bn` and `reason_en`. English quiz content lives in `QuizEnglishSeeder` (run by its migration and by the content seeder; fills only empty fields). Each language has its own OG images (`images/og/en/`). Adding UI text: wrap it, then add the English to `lang/en.json`.

**Map**: the Bangladesh outline (`partials/bd-map-path.blade.php`) is projected from Natural Earth data; location `map_x/map_y` are % positions in the same projection. Map dots are rendered server-side because Alpine `x-for` doesn't work inside `<svg>`.

**Shared shell** (2026-10-10, phase 1 of `docs/2026-10-10_community-first-plan.md`): every public page, quiz and community, uses `<x-site.header>`, `<x-site.footer>` and `<x-site.tabbar>` (`resources/views/components/site/`; sections in `App\Support\SiteNav`). The quiz hides header, footer and tab bar during the questions and the reveal. A signed-in reader's name/avatar are set before the first paint by `partials/me-prefill` (an inline script at the end of the header and tab bar, reading `localStorage['bd.member']`, marks `data-me="in|out|name|letter"`), so the menu doesn't flip from "লগইন" on every page load; Alpine then takes over. Error pages keep their own self-contained layout on purpose (they must render when the app is broken). `LayoutTest` checks every public page in both languages.

**Accessibility** (checked 2026-10-10 with axe-core in both languages, phone/desktop, light/dark, and by keyboard): the header starts with a skip link to `#content` (each page shell puts `id="content" tabindex="-1"` where its content starts); every page has one `h1`, and lists of `h3` cards sit under an `h2` (sr-only where there's no visible one); dialogs are named (`aria-labelledby`); form errors are `role="alert"`; dynamic regions announce a short summary (`aria-live`), never a whole list.

## Conventions

- **Laravel 12 on PHP 8.2** (production host runs 8.2; `config.platform.php` is pinned to 8.2.0 so composer only picks 8.2-compatible packages). Don't use PHP 8.3+ features (typed class constants, `#[\Override]`, `json_validate`) or Laravel 13-only APIs (model/command attributes like `#[Fillable]`/`#[Signature]`, `PreventRequestForgery`). Models use `$fillable`/`$hidden`/`$table` properties, commands `$signature`/`$description`; the CSRF middleware is `ValidateCsrfToken`. Test with `php8.2 artisan test` before shipping. The trait model is `PersonalityTrait` (`Trait` is reserved).
- **Node 18 on the server** (Forge dev box has 18.20.5): front-end tooling is pinned to Vite 6, laravel-vite-plugin 1.x and Tailwind `~4.1.18`. Tailwind 4.2+ and Vite 7+ need Node 20, and npm silently skips Tailwind's native binary on 18. Check a build with Node 18 before bumping them (see `deploy/FORGE.md`).
- Times are Asia/Dhaka: `APP_TIMEZONE=Asia/Dhaka` and `DB_TIMEZONE=+06:00` (MySQL session zone, so `useCurrent()` defaults agree with PHP).
- Styling: Tailwind 4 with semantic CSS-variable tokens in `resources/css/app.css` (`bg-paper`, `text-ink`, `text-ink-2`, `border-line`, `bg-accent` …). Colour roles: `flag-red` is the brand and the main action (the UI token `--red` is `#cf2e35`, a touch darker than the logo's `#e03a3e`, so white on it reaches 4.5:1; red *text* uses `text-red-text`, lighter in dark mode, like `text-green-text`), `danger` is errors and destructive steps, `warn` is "needs attention" (unanswered, help wanted). Long reading uses `.prose-text`. Dark mode is a token swap under `prefers-color-scheme`, so use tokens rather than `dark:` classes. Per-location colour comes from `--accent`.
- User-facing copy is conversational Bangla (with English at `/en`): the quiz pages (`/`, `/r/{code}`, including their community block) use তুমি; community pages, community API messages and toasts use আপনি. Admin UI is English. Never hard-code user-facing text: wrap it (`__()` / `t()`) and add the English to `lang/en.json`.
- Brand mark: `partials/logo.blade.php` (inline emblem, token colours for dark mode; redrawn from the Facebook-page logo on the accurate map outline). Static copies: `public/images/brand/logo.svg`; favicons/app icons are the simpler green tile (white country + red sun) so they read at 16px.
- Place illustrations are placeholder flat SVGs in `public/images/locations/` (400×300 viewBox); the image question reuses them.
- Production needs a correct `APP_URL` (used in share URLs and `og:image`).
- In Blade, a `@php … @endphp` block placed after inline `@php(...)` statements isn't parsed (compiles to a syntax error): keep to inline `@php(...)` there.
- Blade directives need a non-word character before the `@`: `before@endif` is plain text (write `before @endif`), and two run together (`@endif@if`) don't parse.
- Bangla text in PHP regexes needs the `u` flag (without it, `\R` matches byte 0x85 inside letters like "অ").
